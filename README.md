# TimeTrack — Веб-приложение для учёта рабочего времени сотрудников

Минималистичное веб-приложение для учёта рабочего времени сотрудников компании с сохранением состояния (включая активные таймеры) в SQLite после перезапуска, строгой серверной валидацией, расчётом времени за выбранный период и автоматическими тестами.

---

## 1. Что реализовано

1. **Добавление сотрудников**:
   - Валидация имени на бэкенде (обрезка пробелов по краям, запрет пустых строк и строк длиннее 80 символов).
   - Защита от дубликатов без учёта регистра (`COLLATE NOCASE` + проверка перед вставкой, код ответа `409 Conflict`).
   - В качестве демонстрационных данных используются только вымышленные сотрудники (`Anna Test`, `Ivan Sample`, `Maria Example`).
2. **Запуск и остановка таймера с описанием задачи**:
   - При старте таймера в таблице `time_entries` создаётся запись с `start_time` в формате **UTC ISO 8601** (`YYYY-MM-DDTHH:MM:SS.sssZ`) и `end_time = NULL`.
   - Действует правило **один активный таймер на сотрудника**: попытка запустить второй таймер при уже работающем возвращает ошибку `409 Conflict` (дополнительно защищено частичным уникальным индексом SQLite `WHERE end_time IS NULL`).
   - Попытка остановить неработающий таймер возвращает понятную ошибку `400 Bad Request`.
3. **Отчёт за период (`date_from` / `date_to`) и политика границ (Boundary Clipping)**:
   - Валидация дат на сервере: формат `ГГГГ-ММ-ДД`, реальность календарной даты (например, `2026-02-30` отклоняется) и проверка `date_from <= date_to`.
   - **Явное правило для записей, пересекающих границы периода**: выбрано **усечение по границам периода (`clip_to_period`)**.
     - Период `[date_from, date_to]` задаёт интервал в UTC: `[date_fromT00:00:00.000Z, date_toT23:59:59.999Z]`.
     - Если завершённая запись началась до `period_start` или закончилась после `period_end`, в отчёт попадает только её пересечение с периодом:
       $$\text{clipped\_duration} = \max\bigl(0,\ \min(\text{end\_time}, \text{period\_end}) - \max(\text{start\_time}, \text{period\_start})\bigr)$$
     - Например, ночная смена с `23:00 UTC` вчера до `01:30 UTC` сегодня имеет полную длительность `2ч 30м`, но в отчёте за сегодняшний день засчитывается ровно `1ч 30м`. В интерфейсе такие записи помечаются индикатором усечения с показом как полной, так и засчитанной длительности.
     - Незавершённые (активные) таймеры не искажают завершённую сумму за прошлые периоды и отображаются явно со статусом «Активен».
4. **Сохранение данных при перезапуске**:
   - Все данные и запущенные таймеры хранятся на диске в файле SQLite (`data/timetracker.db` в режиме `WAL`). Перезапуск сервера или повторное открытие базы не сбрасывает текущий таймер.

## 2. Как установить и запустить приложение и тесты (≤ 3 команд)

В репозитории доступны два варианта запуска: **Node.js / TypeScript (встроенный модуль `node:sqlite`)** и компактная эталонная версия на **Python 3.11+ / FastAPI / SQLite / pytest** (в папке `python_version/`).

### Вариант А: Node.js 22+ (основное приложение и живое демо)

```bash
npm install
npm test
npm run dev
```

- Приложение открывается по адресу `http://localhost:3000`.
- Команда `npm test` (`npx --yes tsx --test src/utils/tracker.test.ts`) запускает изолированные автотесты на временной БД в `os.tmpdir()`.

### Вариант Б: Python 3.11+ / FastAPI / SQLite / pytest (`python_version/`)

```bash
pip install -r python_version/requirements.txt
pytest python_version/test_app.py
uvicorn python_version.app:app --reload --port 8000
```

Добавь ограничение на уровне БД, чтобы у одного сотрудника не могло быть двух активных таймеров одновременно, и напиши логику старта/остановки с понятными HTTP-кодами ошибок».

2. **Обработка записей, пересекающих границу фильтра дат**:
   > «Реализуй функцию расчёта отчёта за период `[date_from, date_to]` в UTC. Если рабочая сессия началась накануне в 23:00 UTC и завершилась в 01:30 UTC выбранного дня, функция должна усекать интервал по границам периода (`clip_to_period`) и возвращать как полную длительность записи, так и длительность внутри периода».

## 4. Места для ручной верификации и раздел «Найденные и исправленные ошибки»

> **Примечание для ревью (в соответствии с правилами задания)**: Раздел ниже не заполнен вымышленными ошибками заранее. Вместо этого перечислены узкие места сгенерированного кода, которые стоит проверить в первую очередь и при необходимости описать в финальной анкете.

### Узкие места, на которые стоит обратить внимание при проверке:

1. **Граница конца суток `23:59:59.999Z` против полуоткрытого интервала `[date_from, date_to + 1 day)`**:
   - *Где смотреть*: `parseStrictUtcDate` и `computeClippedDuration` в `src/utils/tracker.ts` (а также `get_period_bounds` в `python_version/app.py`).
   - *Суть тонкости*: Сейчас конец периода задан как `T23:59:59.999Z`, а длительность округляется через `Math.round((clippedEndMs - clippedStartMs) / 1000)`. Из-за `.999Z` разница между `00:00:00.000Z` следующего дня и `23:59:59.999Z` составляет `1 мс`, что при `Math.round` даёт точное число секунд (например, `3600` секунд для интервала `23:00:00Z -> 01:00:00Z`), но при `int()` усечении в Python без округления могло бы терять 1 секунду (`3599` с). В `python_version/app.py` поэтому используется полуоткрытая правая граница `next_day 00:00:00Z`.
2. **Часовой пояс фильтра отчёта (UTC против локального времени браузера)**:
   - *Где смотреть*: инициализация дат по умолчанию на фронтенде и `getPeriodReport` на бэкенде.
   - *Суть тонкости*: Все метки времени сохраняются и фильтруются строго в UTC (`ISO 8601`). Если пользователь работает поздно вечером по локальному времени (например, UTC+3 в 01:30 ночи), дата в UTC уже принадлежит новому дню.
3. **Валидация календарных дат (например, `2026-02-30`)**:
   - *Где смотреть*: функция `parseStrictUtcDate`.
   - *Суть тонкости*: В JavaScript `new Date('2026-02-30')` молча переносит дату на `2 марта`. Чтобы это не приводило к скрытым ошибкам фильтрации, добавлена обратная сверка `dt.getUTCMonth() + 1 === m && dt.getUTCDate() === d`.
4. **Учёт еще идущего таймера в итоговой сумме отчёта**:
   - *Где смотреть*: `getPeriodReport` в `src/utils/tracker.ts`.
   - *Суть тонкости*: В `total_seconds` за период суммируются только завершённые записи (`end_time IS NOT NULL`), а наличие активного таймера передаётся флагом `has_active_timer: true` и выводится отдельным живым счётчиком.
